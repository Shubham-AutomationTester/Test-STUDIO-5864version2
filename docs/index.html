Execution guide

Use the repository README and qa/TEST-PLAN.md for the full runbook.

01 / PUBLISH

Render Free Web Service

  1. Upload the extracted contents to a new GitHub repository. Keep render.yaml, tools/, source/ and docs/ at the same level.
  2. Render: New > Web Service. Select Python 3 and the Free instance.
  3. Build: python3 tools/build.py
  4. Start: python3 tools/serve.py --bind 0.0.0.0
  5. Leave Root Directory empty when files are at the repo root. There is no Publish Directory for this service.

Alternative: New > Blueprint reads the included render.yaml. Create a new service, not the old Static Site. Do not add a catch-all rewrite.

02 / VERIFY

Check the deployed response

Open the homepage to wake an idle free service, then check live headers. A cold-start timeout is a hosting issue, not a robots-directive failure.

python3 tools/verify.py YOUR_BASE_URL --require-repeated

Repeated fields are emitted separately at the origin. A proxy can combine them; the strict verifier reports that instead of claiming the raw-field test passed. Browser checks validate combined values only.

Local preview: python3 tools/serve.py --port 8000. SearchStax cannot access your laptop's localhost.

03 / CONFIGURE CRAWL

One scenario per crawl

Open a case and use Copy Start URL. Use a dedicated QA index and clean queue. Disable sitemap discovery, imports and other Start URLs. Keep the scenario's child paths in scope; depth at least 5, item budget at least 500.

The R-cases start at an allowed entry, for example /cases/r06/, which discovers its blocked parent. This avoids any special handling of robots-disallowed Start URLs.

Run each selected scenario with Ignore robots.txt OFF and ON in separate clean runs. Preserve the index only for lifecycle tests.

04 / BOT IDENTITY

Default: SearchStax Crawler

<meta name="SearchStax Crawler" content="noindex">
X-Robots-Tag: SearchStax Crawler: noindex

The meta name uses the default supplied by QA. Record the full observed HTTP User-Agent separately. Scoped-header support and conflict resolution are explicit product-decision cases, not silently assumed.

05 / OBSERVE

Measure different pipeline outcomes

noindex: parent can be fetched/processed but cannot add or update its document. Its ordinary child remains eligible.

nofollow: parent can index; no child may be enqueued from its links. A separate permitted occurrence can still enqueue the same target.

Record app ID, crawl definition/run IDs, timestamps, actual User-Agent, response headers, queue provenance and Solr/index document evidence. Do not infer queue behavior only from search-preview absence.

06 / SAME-URL UPDATES

Use the lifecycle phases

python3 tools/build.py --phase baseline
python3 tools/build.py --phase restricted
python3 tools/build.py --phase restored

These are three separate deploy-and-crawl steps, not commands to run back-to-back. Keep the same parent URL and existing index. Force a real re-fetch after each deployment.

U01/U02 prohibit a V2 update under noindex. Retention versus deletion of V1 is not defined by the ticket. U03/U04 introduce a previously undiscovered child to avoid stale-queue false failures.

!
Do not turn assumptions into release-blocking defects.

The ticket is the acceptance contract. Google behavior is useful background, not a substitute for SearchStax-specific precedence.
